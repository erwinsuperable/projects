Bloom — the FACES design system

A working component library and token architecture modeled on the FACES beauty e-commerce experience (faces.com / faces.ae): deep racing green on white, squared geometry, dense merchandising badges, AED pricing patterns, and first-class English/Arabic bidirectional support.

Throughout the docs, Observed marks patterns taken directly from the live site (colors approximated from screenshots and assets), while Proposed marks improvements this system adds — e.g. a formal token scale, visible focus states, skeleton loading, and semantic status colors.

Color

Brand green ramp anchored on the FACES logo green Observed; full 50–950 ramp, blush accent, and semantic statuses are additions for scalable UI work Proposed. Click any swatch to copy its token. All text/background pairs used in components meet WCAG 2.1 AA (≥4.5:1 body, ≥3:1 large/UI).

Neutrals & accents

Semantic

Do
  • Reserve green-900 for primary actions, active nav, and the USP bar.
  • Use error-600 for sale prices and destructive actions only.
  • Reference semantic aliases (--ds-brand, --ds-sale) in components, not raw hex.
Don't
  • Don't place green-500 text on white for body copy — it fails AA at small sizes.
  • Don't invent new tints; extend the ramp through a token proposal.
  • Don't use sale red for badges and success moments simultaneously in one card.

Typography

FACES uses a clean grotesque sans across UI and merchandising Observed. Bloom pairs Archivo (variable width lets the wordmark sit wide at 112%) with Tajawal for Arabic — matched x-height and weight range so mixed-script pages feel like one voice Proposed. Type scale is a 1.25 ratio from a 16px base.

Do
  • Keep body line length under 80 characters.
  • Uppercase only brand names on cards and the VAT caption.
  • Use numerals in the locale's convention; prices keep Western digits in both languages, as on the live site.
Don't
  • Don't letterspace Arabic text — Tajawal must run at 0 tracking.
  • Don't go below 12px for any customer-facing text.
  • Don't mix a third typeface for campaigns; use Archivo's width axis instead.

Buttons

Primary green fill drives commerce actions ("Add to Bag", "Go to Checkout") Observed. Squared 2px radius; labels are verbs in sentence case. Loading and disabled states are additions Proposed.

VariantUse forSpec

GhostTertiary/inline actions inside dense UIno border, green text
DangerDestructive confirmation only — never for sales CTAsbg error-600
Do
  • Say what happens: "Add to Bag", "Go to Checkout".
  • Keep one primary button per card/section.
  • Show a spinner and set aria-busy while an add-to-bag request runs.
Don't
  • Don't use "Submit" or "OK" as labels.
  • Don't shrink below 44px height on touch layouts.
  • Don't disable a button without explaining why nearby.

Notifications

Inline alerts hold page-level status; toasts confirm quick actions and self-dismiss after 4s. Toasts render into a polite live region so screen readers announce them without stealing focus.

Modals & drawers

Modals interrupt for a decision; drawers extend the page for browsing tasks (cart, filters on mobile). Both trap focus, close on Esc and overlay click, and return focus to their trigger. The cart drawer slides from the end edge — right in LTR, left in RTL.

RTL & localization

Arabic is a first-class experience, not a mirrored afterthought. Use the language toggle above — the storefront demos, badges, buttons, filters, and cart translate, the document flips to dir="rtl", and Tajawal takes over.

RuleImplementation
Layout flips automaticallyLogical properties only: margin-inline-start, inset-inline-end, padding-inline — never left/right physical values
Drawers & badges follow reading directionCart slides from the end edge; badges anchor top-start, wishlist top-end
Directional icons mirrorChevrons/arrows flip via [dir="rtl"] .mirror{scale:-1 1}; search, bag, heart do not
Prices stay legibleWestern digits with the AED unit after the number in both locales, matching the live site; wrap prices in dir="ltr" spans inside Arabic sentences
No tracking on ArabicLetterspacing tokens apply to Latin only
Strings live outside markupAll UI copy keyed in a locale dictionary; no concatenated sentences

Naming & governance

Token architecture

TierPatternExample
1 · Primitive{category}.{hue}.{step}color.green.900 → --ds-green-900
2 · Semantic{intent}[.{state}]color.brand.hover → --ds-brand-hover
3 · Component{component}.{prop}button.bg → --btn-bg (scoped)

Component conventions

Class names.ds-{component}, modifiers .ds-{component}--{variant}, states .is-{state} (is-loading, is-error, is-oos)
Variants before sizesclass="ds-btn ds-btn--secondary ds-btn--sm"
States are additiveState classes never restyle variants — they layer on top, so any variant can load or disable
ContributionNew tokens/components enter via proposal → a11y review → documented here with Observed/Proposed provenance before use
Do
  • Compose pages only from documented components.
  • Keep hard-coded values out of feature code — everything through tokens.
  • Test each new component in Arabic before shipping.
Don't
  • Don't fork a component for a campaign; theme it with tier-3 tokens.
  • Don't add a third badge to a product card.
  • Don't ship a state (error, empty, loading) that isn't designed here first.
